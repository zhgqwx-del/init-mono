# 三仓 feature 接手示例

一个前端、业务 API 和领域 API 需要共同交付「活动列表展示名额并筛选可报名活动」。

先根据三个项目的实际位置、负责人、API 契约、身份传递及启动测试方式建立系统地图。将需求写成同一份规格。示例约定剩余名额为名额减已预订数且最低为零，只有进行中且有剩余才可报名。

业务 API 聚合领域 API，筛选后再计数和分页。前端提交筛选条件，翻页用已提交条件。领域 API 提供批量查询并保证数据可见范围。对旧调用保留原字段，新依赖异常时定义可观察的失败行为。

用 mono-start 为涉及的三个仓库建独立任务工作树，确认可运行的基线，再用新判据得到实际失败。Agent 跨仓实现，人处理业务取舍与评审。mono-verify 既跑各仓测试，也让真实请求从前端经过两个 API，按共同判据记录三仓版本与实际响应。

mono-wrap 汇总各仓提交或 PR，写清后端二、后端一、前端的兼容发布顺序和恢复路径，把系统决定写回共享上下文。需要几个项目参与，由该 feature 的影响面决定。

完整可运行示例在脚手架分发仓库的 examples/three-services 中，包含旧项目种子、参考补丁、失败到通过的操作步骤、HTTP 和浏览器验收。用现有团队项目时替换输入，结合实际业务重新确定约定。
