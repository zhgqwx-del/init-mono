# 跨项目工作流程

共享资料提供系统地图和团队规则。Agent 按当前任务读取需要的仓库、业务契约和历史决定。按项目维护可执行的启动和测试入口，让后续会话能复用同一环境和成功判据。

## 开始与接手

mono-start 从任务目标定位调用方、提供方和已有测试。先核对基线可运行，整理涉及的交互、API 或事件、缺省与错误行为、数据范围、兼容顺序及影响项目。人决定有歧义的业务规则和取舍，Agent 将规则转成有输入与预期的验收判据，并据此组织跨项目改动。

按需求建立隔离工作树，各项目分别提交，用同一个任务号关联。同一人协调交付结果。若工作由多个人或会话接力，在任务目录记录实际进展、正在使用的版本、已作决定及需要他人处理的事项。并行任务的端口、数据库、测试账号和分支也应按项目条件隔离。

## 执行与诊断

Agent 按共同规格实施，复用各仓现有做法。新发现的接口冲突、产品取舍或架构变更带给负责人确认，已有授权允许继续的技术工作继续推进。一次明确业务判断形成可链接的决定记录，避免后续会话重新猜测。

缺陷任务先记录复现条件和受影响版本，利用已获准的日志、配置或错误报告定位。用能失败的用例复现，再实现并验证修复。日志访问范围和代码修改权限依各项目既有安排执行。

## 联合验收

mono-verify 运行仓内测试，再从调用方的真实入口走到依赖方，覆盖核心成功路径、已约定边界、兼容和数据范围。按 AC 记录预期与实际，保存实际运行证据及相关版本。有条件时由另一位同事或独立验证会话复跑关键用例。

scripts/mono.py 的回执绑定共享规格与各项目当前内容，check 可发现代码或规格改变后的旧证据。测试通过只说明覆盖过的判据成立。产品质量和上线取舍由负责人结合结果判断。没有机器可判定终点的工作，由人给出完成决定。

## 交付与复盘

mono-wrap 汇总受测提交、跨项目 PR、版本依赖和剩余问题。按项目现有规则组织合并、灰度和发布，记录冒烟、监控、停止和恢复方式。尚未要求发布时，完成可审查的交接记录即可。

记录需求确认到验收或上线的周期、人工投入、等待、返工、质量问题及可获取的模型成本。用这些记录判断收益是否来自减少交接。把通用规则和运行方式更新到共享文档，控制同时推进的任务数量，让需要人决定的事情可见。
